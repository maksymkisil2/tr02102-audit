# Roadmap

Small, ordered tasks that bring tr02102-audit to a finished, verifiable state.
Each task fits into one working session and is done only when its acceptance
criterion is covered by an automated check that passes in CI
(`ruff check`, `ruff format --check`, `mypy`, `pytest`).

Rules for every task: no features outside this list, no secrets in the
repository, keep `CHANGELOG.md` (section *Unreleased*) and the affected docs up
to date, and tick the box in the same pull request.

## P1 — Correctness of the checks

- [ ] **Rule-file schema test.** A test loads every file in `standards/` and asserts: unique rule IDs across all files, non-empty `title`, `reference` and `remediation`, `severity` from the allowed set, known `check.op` and `check.subject`, and the top-level fields `edition`, `url` and `transcription`. A malformed rule fails the test with the file name and rule ID.
- [ ] **Boundary tests for BSI TR-02102-2.** For each of the 19 BSI rules, one synthetic observation that passes and one that violates it (parametrised test in `tests/test_rules_bsi.py`). Expected verdicts are asserted per rule ID.
- [ ] **Boundary tests for NIST SP 800-52r2.** Same structure as the BSI task, in `tests/test_rules_nist.py`.
- [ ] **Boundary tests for IETF RFC 9325 and PCI DSS 4.0.1.** Same structure, one test module per standard.
- [ ] **Boundary tests for NCSC-NL 2025 and both Mozilla profiles.** Same structure, one test module per standard.
- [ ] **Deterministic clock for "use up to" years.** Rule evaluation takes the current date from one injectable function. Tests freeze the date on 31 December and 1 January of a phase-out year and assert that the verdict changes exactly at the boundary.
- [ ] **X.509 edge cases.** Tests with certificates generated by `cryptography`: RSA 2048 vs 3072 bits, P-256 vs P-384 vs brainpoolP256r1, SHA-1 signature, expired and not-yet-valid, missing SAN, hostname mismatch. Each case asserts the finding the analyser reports.
- [ ] **Robustness of the TLS wire parser.** Seeded random and truncated inputs (standard library only, no new dependency) for the record and handshake parsers in `tls/wire.py`. Any input either parses or raises the documented parse error; no other exception, no hang. Fix every crash the test finds.
- [ ] **Coverage gate.** Add `pytest-cov` to the `dev` extra, report line and branch coverage in CI, and fail below the coverage measured when the task starts (rounded down). Document the number in the README *Quality* section.

## P2 — Container, CI and supply chain

- [ ] **Hardened container image.** Multi-stage build, base image pinned by digest, `HEALTHCHECK` on `/healthz`. A CI step runs the image with `--read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges` and the existing probes still pass.
- [ ] **Image vulnerability scan.** The *Security* workflow builds the image and scans it with Trivy (action pinned by commit SHA). The report is uploaded as SARIF artifact; the job fails on CRITICAL findings that have a fix.
- [ ] **SBOM for the image.** Generate a CycloneDX SBOM of the container image in CI and upload it as a build artifact. The README explains where to find it.
- [ ] **Workflow security lint.** Add `actionlint` and `zizmor` checks for `.github/workflows/` to CI. Fix every finding or document an accepted one inline.
- [ ] **Python version matrix.** The *quality* job runs on Python 3.13 and 3.14. `pyproject.toml` classifiers match the matrix.
- [ ] **Pre-commit hooks.** `.pre-commit-config.yaml` runs the same ruff and mypy versions as CI; `CONTRIBUTING.md` explains the setup. A CI step asserts that the hook versions equal the pinned `dev` versions.

## P3 — Hosted web version (Render, password login)

- [ ] **Session and login security tests.** Explicit tests for: cookie flags `Secure`, `HttpOnly`, `SameSite`; session rotation after login; failed-login rate limit or lockout; CSRF token on every state-changing form; security headers including CSP. Fix any gap the tests reveal.
- [ ] **Fail-closed production configuration.** In production mode the app refuses to start with a missing or short `SECRET_KEY` or `APP_PASSWORD`, and logs a clear reason. Tests cover each refusal.
- [ ] **Deployment runbook.** `docs/DEPLOYMENT.md`: Render setup, environment variables, PostgreSQL, rotating the admin password, backup and restore. A test asserts that every `envVars` key in `render.yaml` is documented there.

## P4 — Documentation as an engineering case study

- [ ] **Link check for the docs.** A test resolves every relative link and anchor in `README.md`, `docs/**/*.md` and `examples/README.md` and fails on a broken one.
- [ ] **Missing architecture decision records.** ADRs for: own TLS handshake implementation instead of the `ssl` module, policy as versioned YAML data, SQLite by default with PostgreSQL for hosting, one gunicorn worker. `docs/adr/README.md` indexes all ADRs; a test asserts that the index lists every ADR file.
- [ ] **STRIDE model for the hosted deployment.** Add a Mermaid data-flow diagram for browser → Render proxy → gunicorn → PostgreSQL with its trust boundaries to `docs/THREAT_MODEL.md`, and threat rows for each new flow. A test asserts that every test file named in the *Verification* column exists.
- [ ] **Mermaid diagrams validated in CI.** A CI step renders every Mermaid block in the docs with `@mermaid-js/mermaid-cli` and fails on a syntax error.
- [ ] **README as engineering case study.** Restructure the README into: problem, constraints, design (linking the ADRs), verification (tests, lab, differential validation), results, limitations, lessons learned. Keep it under 250 lines; move details to `docs/`. The link-check test passes.
